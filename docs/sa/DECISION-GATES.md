**Outcome vocabulary:** PASS discharges only the stated decision, not its entire SA/FX family. A semantic mismatch is failure; a correctly rejected unsupported input is safety evidence with capability still open. Infrastructure failure means unavailable, not negative architecture evidence. A trustworthy oracle that cannot interpret a new CFG/op returns ORACLE_INSUFFICIENT. No result permits dropping paths, inventing entry facts, weakening proof checks or changing the expected answer to fit returned metadata.

**Budget:** each gate has one small fixture family, the listed sensitive negative, one initial witness and at most one localized correction with one confirming rerun. Cap focused investigation at **two engineering days per gate**, excluding time waiting for infrastructure; convert remaining work into the specified implementation task instead of expanding the campaign. G3's two related subchecks share this single budget. Repeated identical GUI launch failures are outside the budget. Any genuinely independent fifth architectural blocker must be named and separately authorized; it is not silently folded into these gates.

**Small witness is not final scope:** the two-path G2 and small RAM/image G3 cases choose an implementation direction efficiently. Their fixture limits and investigation budgets do not become final support restrictions. The implementation packages must generalize beyond them to the complete SA/FX requirements; a successful gate does not waive unknown pointers, richer control flow, asynchronous/device effects or other required domains.

## G1 — Normal window, dependency invalidation and explicit refresh

**Reused evidence/source.** Use a new disposable copy of saved `projects/baseline-F12-r2.gpr` plus its `.rep` directory, Program `/P.gb`, from the selected workspace. Its proof/payload/current-candidate reopen are qualified in [EX-02-05][report] and [F12 reopen receipt][reopen]. The existing headless checker supplies the B-parity/value/effect oracle. EX-02-05 display selection and P/Q interfaces do **not** establish a window-owned result. The [historical AWT record][gui] remains blocked; there is no reason to repeat the same failed facility.

Pinned `DecompilerProgramListener` in the runtime [Decompiler source archive][upstream] resets the native controller for memory-block add/remove/restore, observes spec changes, and schedules refresh on received Program events. `DecompilerController` has its own Function-result cache; `refreshDisplay` clears it. Provider `doRefresh` and the built-in Refresh action use that controller. Thus the missing fact is runtime ownership/event delivery and application integration, not whether stock source contains any invalidation mechanism.

**Smallest positive witness, future sequence.** In one genuinely available normal CodeBrowser session using copied runtime/project/profile: open the saved alias in the actual normal Decompiler window, observe its conditional header and B-dependent result; change only consumed file A000 from A7 to D4 in the same live Program while retaining its old registration; let real Program events and the normal controller update; then explicitly regenerate the proof through the provider's refresh action and use ordinary window refresh. No topology creation is needed during the measured sequence. W5 may first need the thin ordinary preview/refresh action, since the current bridge is exposed chiefly by capture tooling.

**Sensitive negative.** The pre-mutation native output is correct for A7 but wrong for D4. After event delivery/debounce has settled, that old generation must not remain presented as a current validated result. Before explicit proof refresh, the old registration must refuse or the UI must clearly mark its result stale/unavailable; after refresh the window must compute the D4 relation. A separate valid DecompInterface producing D4 cannot rescue stale window output.

**Observable/oracle.** Record actual provider/window identity, Program live/persistent identity, selected Function/alias, proof/dependency generation and visible C/markup. **First capture passively, after the Program event/debounce drain and before any Debug or Refresh action.** Pinned public APIs provide `DecompilerProvider.getDecompilerPanel().getController().getDecompileData()`; the current `DecompileData` exposes Program, Function, HighFunction, C markup, results and errors without issuing a new request. Capture that currently displayed result and its stale/current disposition, with a screenshot where the facility permits. Do not reflect into private fields or substitute a parallel decompiler. The built-in Debug Function Decompilation action calls `refreshDisplay`, which clears the controller cache: use it only as separately labeled window-owned payload evidence after the passive observation, never as proof that ordinary event invalidation worked. Any subsequent explicit provider proof refresh and window Refresh are separate recorded actions. Where native PID is captured, bind it to that window's serialized lifecycle, not just a list of children. Evaluate the passive HighFunction and later debug-linked results with the retained oracle or a narrow CFG adaptation; report errors and event-drain timeout explicitly.

**Bound/consequences.** One Program, one byte mutation, one explicit refresh, one usable GUI session. Stop on the first identical environment failure. PASS supports the stock-listener-plus-thin-service approach. Missing Program events requires a W5 event publication fix; stale controller reuse after correct events requires a W5 supported controller integration fix. Correct window-owned payload but wrong native result becomes a localized lowering/transport defect. Safe stale refusal passes safety only until refreshed positive behavior succeeds. If the GUI remains unavailable, retain the implementation direction, complete other packages and mark A-GHIDRA/normal-window release acceptance blocked. Do not add a custom decompiler window just to claim success.

## G2 — Branching, same-CPU bank identity and real calls

**Reused evidence/source.** [SoftwareCallStatePathsTest][state-tests] explicitly says its branch checks use two exact flag premises, not one unknown-flag CFG. [SoftwareCallStateCalleeApplicationTest][callee-tests] already covers native competing PCs, physical data identity, nested ordinary call restoration and two selected same-Program contexts. Reuse those frame/target expectations; do not retest every wrapper convention. EX-03-03/C supplies bank-changing fetch transport; EX-02-04/05 supplies unknown-byte selector relationships. [OrdinaryEntryAccess][ordinary] refuses branches/calls and `orderedFetch` rejects multiple states at one instruction; [SoftwareCallEffects][effects] is an existing exact-state graph foundation.

**Missing decision.** Determine whether extending producer/predicate state is sufficient to carry one unresolved-input control-flow graph through existing state-qualified transport, or whether graph identity, local lowering or Ghidra Function representation must change. Ordinary adapter refusal on a branch is a known missing capability, not proof the representation is inadequate.

**Smallest positive witness.** Adapt one existing four-bank fixture: at a fixed-ROM entry, an unknown input byte's low bit selects bank 1 or 2 on two real branches; both paths join at one fixed-ROM CALL site targeting the same CPU address in ROMX. Bank 1 and bank 2 contain different short callee bytes there, yielding distinguishable register/WRAM results, each returning through the actual saved return word to the same caller continuation. Preserve the input predicate and live mapper state through the CALL/RET. Use one ordinary CALL convention, one call depth, two paths and one output cell. All relevant byte completions must be represented by one admitted graph, not two separately specialized Programs presented as an unknown-input result.

**Sensitive negative.** Deliberately key the checker/model cache by CPU PC without physical/domain identity, or swap the bank-to-callee edge while retaining plausible output constants. The oracle must detect the wrong branch-to-physical-target/return relationship. A second negative may omit the real stack push in the existing call oracle; no new wrapper family is required.

**Observable/oracle.** Compare raw architectural execution against graph nodes/edges and access ledger, then emitted operations and native HighFunction/C. Assert both reachable predicate paths, exact physical fetched bytes, CALL destinations, continuation CPU/physical view, SP delta and return word, bank state, register/flag effects and ordered WRAM stores. Exhaust all 256 relevant input bytes; vary irrelevant inputs only where their dependence is claimed. Extend the retained one-block checker only for this small diamond/call form with independent branch/frame expectations; unsupported forms remain ORACLE_INSUFFICIENT.

**Bound/consequences.** One diamond, two physical callee bodies at one CPU target, one call/return, initial candidate plus one localized adapter/correction. First reuse exact-state evidence to avoid rediscovering already solved stack/native issues. Correct graph rejected by a linear admission guard means W3 producer/dispatch generalization; merged physical nodes means W3 identity correction; correct graph and wrong emitted edges means W3 lowering; correct emitted graph and wrong native Function/flow recovery is evidence to reconsider D1/D2 at that boundary. Repeated safe refusal keeps multi-path capability open; it must not stall W1/W2 or exact-context maintenance. Fallback: maintain explicit conditional contexts while implementing predicate-partitioned graphs and, only if necessary, a narrowly revised view/protocol representation. No global address widening or whole architecture replacement is automatically authorized.

## G3 — Symbolic RAM effects and executable-image lifetime

**Reused evidence/source.** Existing ordinary tests/checkers establish ordered mapper stores and immutable reads; `SoftwareCallEffects` already tracks exact physical memory bytes/writes, and `ProgramMapping` distinguishes original/current file bytes and identifies RAM storage. Existing current-ROM patch stale/refresh checks establish only that patch lifecycle. They do not prove arbitrary mutable RAM, hidden writers, copied code or replaced executable images. [Effects][effects], [mapping][mapping], [finite controls][report]

**Missing decisions.** (a) How to preserve a symbolic RAM input and alias-aware write/read relationship in native output without treating initialized Program memory as an entry fact; (b) how image generation and provenance invalidate code/proofs independently of physical address and source-ROM bytes. Record separate results for these two subchecks; both are needed for G3 PASS.

**Smallest positive witnesses.** Use the same self-authored ROM/Program infrastructure for two tiny routines. For memory, read one fixed-WRAM byte whose entry value U is explicitly unknown, store U to an observable cell, write U+1 through its justified echo alias, then read the original physical byte and store that result to a second cell. The expected relation is `(U, U+1 mod 256)`, not the loader's initialized byte. This is deliberately a bounded mutable-memory witness, not a substitute for original U_PTR/general unknown-pointer/device capability.

For lifetime, use two short, known initialized code images at the same WRAM CPU location, each with a different visible effect/return. Establish the first image's initializer/source and generation; replace its RAM bytes with the second image while retaining the old executable proof. The old generation must not decode/decompile as current. Explicitly establish/decode the new image and derive its new view. A separate change to the source ROM after copying must not retroactively change the existing RAM image. This distinguishes storage identity, source provenance and executable-image lifetime.

**Sensitive negatives.** Feed initialized zero as U or remove/reorder the alias store: the full-byte relation must fail. Add one possible external/unknown aliasing write in the model and require dependent memory facts to weaken while proved disjoint state survives. For images, reuse an address-only cache/proof for the old generation after replacement; require stale refusal even when the address/name remains identical. Same bytes copied from a different declared lifetime must not accidentally transfer live proof authority.

**Observable/oracle.** Exhaust U's byte domain for the two memory outputs, ordered accesses and physical alias identity. Inspect actual lowered LOAD/STORE/effect dependencies and optimized native results separately. Compare old/new image byte hashes, initializer provenance, generation, decoded instructions, proof/view ownership and stale/current results; include a targeted saved/reopened image-generation check when the new image contract is persisted. No imported zeroes, permanent ROM-backed RAM aliases, global volatility or writable-ROM workaround. Device/timing summaries may be conservative, but required uncertainty stays visible.

**Bound/consequences.** One symbolic byte and alias pair, two small code images, one replacement, at most one local memory/lifetime correction. Do not extend into full timer/DMA/interrupt emulation. Lost symbolic values or alias effects requires W2/W4 memory/effect work; stale code acceptance requires image-generation/dependency/application repair in W4/W5. Only a correct effect payload that native optimization cannot preserve warrants changing the native/effect adapter. Safe refusal is acceptable containment, not mutable-memory capability PASS. Fallback: expose unresolved effects with precise alias kill sets and refuse unestablished executable images while implementing W4; immutable-ROM and exact-context work continues.

**Bound/consequences.** One actual registry-4 Program, one edited variant, one candidate migration/rejection policy and one rollback/cancellation checkpoint, within the shared two-day gate cap. This witness does not qualify every historical registry, language version, debugger consumer or exotic topology.
